## 🎯 本关学习目标

在前面的 19 个关卡中，我们攻克了屏幕显示、触控交互、网络通信、蓝牙透传、文件系统与低功耗休眠等几乎所有单点外设驱动。然而，当这些模块要同时塞进同一个复杂商业产品中时，初学者往往会陷入巨大困境：
* **“代码写成了一锅粥”**：一个 `app_main.c` 堆叠了数千行代码，改动一个按键引脚，导致整个网络通信莫名其妙报错；
* **“模块间死死绑定”**：传感器模块直接调用 UI 刷新函数，想把数据再发给 MQTT 云端时，代码改得面目全非；
* **“设备跑几天就死机”**：程序偶尔卡死死锁，没有任何保护与自愈机制，更无法定位到底是哪一行代码导致崩溃。

本关我们将完成从“单片机业余玩家”到“企业级嵌入式系统架构师”的最关键思维蜕变 —— **掌握工业级三层模块化分层架构、统一事件总线、有限状态机与高可用看门狗守护自愈体系**！

### 🏆 核心技能清单：
1. **掌握 BSP（板级支持包）分层设计**：实现硬件驱动与业务逻辑彻底解耦，上层代码 0 硬件寄存器细节；
2. **掌握统一事件总线（Event Bus）发布-订阅通信**：彻底斩断跨模块直接依赖，实现广播式多路分发；
3. **掌握有限状态机（FSM）生命周期管理**：用严密的状态转移模型消除多层 `if-else` 地狱；
4. **掌握高可用运维双保险（TWDT 看门狗 + Core Dump 崩溃诊断）**：
   - 🐕 **TWDT 任务看门狗**：超时死锁硬件自动复位自愈；
   - ✈️ **Flash Core Dump 黑匣子**：掉电不丢失，命令行秒级反解崩溃源码行！
5. **掌握工业级多文件工程组织与构建**：标准 `bsp/`、`services/`、`app/` 三层架构实战！

## 20.1 为什么要软件分层？从“面条代码”到工业级架构

在前面的关卡中，为了让初学者快速上手看到声光电效果，很多实验都将 GPIO 配置、传感器采集、算法计算和屏幕绘制写在了同一个 `app_main.c` 甚至同一个循环体中。这种写法在玩具级项目中尚可应付，但在工业级商业产品（如大疆无人机、扫地机器人、智能中控台）中，如果代码写成一团乱麻，被称为 **“面条代码（Spaghetti Code）”**。

### 🚗 生活化比喻：开汽车与造汽车
想象一下开汽车：
* **业务驾驶员（App 层）**：你只需要踩油门（`car_accelerate()`）、踩刹车（`car_brake()`）、打方向盘（`car_steer()`），你**根本不需要知道**发动机是 4 缸还是 6 缸，火花塞是在哪根引线点火，节气门开度用了多少毫伏电压！
* **底盘与发动机工程师（BSP 底层驱动）**：他们负责把火花塞点火、刹车油泵压力、转向助力马达控制好，给驾驶员提供油门踏板、刹车踏板和方向盘这三个标准操作把手。
* **分层的好处**：今天把汽油发动机换成纯电动马达（底层硬件彻底更换），**驾驶员开车的操作动作（上层业务代码）完全不用重新学，一行都不用改！**

```text
 ┌────────────────────────────────────────────────────────────────────────┐
 │                    【没有 BSP  VS  拥有标准 BSP 分层】                 │
 │                                                                        │
 │  ❌ 没有 BSP（硬编码惨剧）：                                            │
 │     业务代码 ──► gpio_set_level(GPIO_NUM_27, 1);                       │
 │     💥 痛点：如果硬件改版把 LED 改接 GPIO18，必须去 10 个业务文件搜索替换! │
 │                                                                        │
 │  ✅ 拥有 BSP（优雅分层）：                                             │
 │     业务代码 ──► bsp_led_set(true);  (纯语义化，完全不知道是哪个引脚)  │
 │     BSP 驱动 ──► #define BSP_LED_PIN GPIO_NUM_27  (底层引脚集中收拢)   │
 │     🌟 优势：硬件改版只需改 1 行引脚宏定义，上层 10,000 行业务代码 0 修改! │
 └────────────────────────────────────────────────────────────────────────┘
```

### 🏛️ 企业级三层经典金字塔架构

在嵌入式软件体系中，最经典的工业级架构自上而下划分为三层：

```text
 ┌────────────────────────────────────────────────────────────────────────┐
 │ 【应用业务层 (App / UI)】                                             │
 │  • 负责业务流转调度、用户交互流程、LVGL 界面显示、云端业务逻辑         │
 │  • 0 硬件寄存器细节！完全不知道具体芯片型号与引脚号                    │
 ├────────────────────────────────────────────────────────────────────────┤
 │ 【系统服务与中间件层 (Services / Middleware)】                         │
 │  • 统一事件总线 (Event Bus)：模块间解耦广播发布与订阅                  │
 │  • 全局生命周期状态机 (FSM)：统筹设备在待机/工作/告警状态间跳转        │
 │  • 任务看门狗 (TWDT) 与 Core Dump：系统死锁自愈与崩溃黑匣子诊断         │
 ├────────────────────────────────────────────────────────────────────────┤
 │ 【板级支持包驱动层 (BSP - Board Support Package)】                     │
 │  • 直接与硬件原理图绑定：屏幕 ST7789、按键消抖、传感器 ADC 硬件采样    │
 │  • 对外屏蔽所有 GPIO 编号，仅暴露极其简洁的语义化 C 语言函数接口       │
 ├────────────────────────────────────────────────────────────────────────┤
 │ 【芯片 HAL / 原厂驱动】ESP-IDF 官方外设驱动 (Driver / FreeRTOS 内核)  │
 ├────────────────────────────────────────────────────────────────────────┤
 │ 【物理硬件 Board】ESP32 主控、ST7789 屏幕、CST816S 触摸、外围传感器电路   │
 └────────────────────────────────────────────────────────────────────────┘
```

#### 🏢 工业界大厂的分工实态（大疆 / 小米 / 华为）：
在正规嵌入式研发团队中：
1. **BSP 底层驱动工程师**：看电路原理图、查芯片手册（Datasheet）、配置底层寄存器与时钟、编写 DMA / SPI / I2C 驱动，输出标准简洁的 `bsp_xxx.h`；
2. **应用/业务工程师（App / UI）**：**无需看硬件原理图**，直接调用 BSP 接口，专注实现业务闭环。

#### 📄 典型 BSP 模块的标准代码骨架示范：
```c
/* ======================== 1. bsp_led.h (对外暴露给业务层的标准接口) ======================== */
#pragma once
#include <stdbool.h>

void bsp_led_init(void);          // 业务层只管初始化
void bsp_led_set(bool is_on);     // 业务层只管开/关 (0硬件细节)
void bsp_led_toggle(void);        // 业务层只管翻转

/* ======================== 2. bsp_led.c (底层内部封装，硬件引脚细节藏在这里) ======================== */
#include "bsp_led.h"
#include "driver/gpio.h"

#define BOARD_LED_PIN   GPIO_NUM_27  // 硬件引脚宏定义只在 .c 内部收拢！

void bsp_led_init(void) {
    gpio_reset_pin(BOARD_LED_PIN);
    gpio_set_direction(BOARD_LED_PIN, GPIO_MODE_OUTPUT);
}
void bsp_led_set(bool is_on) {
    gpio_set_level(BOARD_LED_PIN, is_on ? 1 : 0);
}
void bsp_led_toggle(void) {
    static bool state = false;
    state = !state;
    bsp_led_set(state);
}

/* ======================== 3. app_main.c (上层业务调用，极度清爽) ======================== */
void app_main(void) {
    bsp_led_init();
    while (1) {
        bsp_led_toggle(); // 优雅调用，未来板子改版换引脚，app_main 一行不用改！
        vTaskDelay(pdMS_TO_TICKS(500));
    }
}
```

## 20.2 统一事件总线（Event Bus）与发布-订阅模式

### ① 什么是事件总线？（城市广播电台机制）
传统的模块间通信通常是“A 模块直接调用 B 模块的函数”（强耦合）。  
例如传感器测到了新温度，如果代码直接写 `ui_update_temp(26.5);` 和 `mqtt_upload_temp(26.5);`，那么传感器模块就必须同时依赖 UI 模块和 MQTT 模块。

而在现代事件驱动架构中，引入了 **事件总线（Event Bus）**：

```text
 ┌────────────────────────────────────────────────────────────────────────┐
 │                    【统一事件总线 (Pub/Sub) 运行模型】                 │
 │                                                                        │
 │    ┌────────────────────────┐                                          │
 │    │ 📡 生产者：后台传感器  │                                          │
 │    │ (只负责往总线抛出数据) │                                          │
 │    └───────────┬────────────┘                                          │
 │                │ esp_event_post("气温更新: 26.5°C")                    │
 │                ▼                                                       │
 │    ════════════════════════════════════════════════════════════════    │
 │    📢 【全局系统事件总线 SYSTEM_EVENT_BUS】(城市广播电台)              │
 │    ════════════════════════════════════════════════════════════════    │
 │                │                      │                      │         │
 │     (自动分发) │           (自动分发) │           (自动分发) │         │
 │                ▼                      ▼                      ▼         │
 │      ┌──────────────────┐   ┌──────────────────┐   ┌─────────────────┐ │
 │      │ 🖥️ 消费者 1: UI  │   │ ☁️ 消费者 2: MQTT │   │ 💾 消费者3: TF卡 │ │
 │      │ (刷新屏幕温度卡片)│   │ (推送数据到阿里云)│   │ (追加写入 CSV)  │ │
 │      └──────────────────┘   └──────────────────┘   └─────────────────┘ │
 └────────────────────────────────────────────────────────────────────────┘
```

* **最大优势**：
  * **生产者与消费者完全互不认识**！传感器任务根本不知道有几个模块在使用数据；
  * 如果未来要增加一个“蓝牙手机同步功能”，**只需新写一个消费者向总线订阅事件，原有的传感器和 UI 代码 0 行修改**！

#### 📄 统一事件总线 (Event Bus) 标准代码骨架示范：
```c
#include "esp_event.h"

// 1. 定义事件基底与具体事件 ID
ESP_EVENT_DEFINE_BASE(SYS_EVENT);
enum {
    EVT_TEMP_UPDATE = 1,  // 温度更新事件
};

// 2. 消费者订阅者：UI 界面监听回调函数
static void on_temp_update_ui(void *arg, esp_event_base_t base, int32_t id, void *data) {
    float temp = *(float *)data;
    printf("🖥️ [UI 消费者] 收到总线广播，屏幕刷新温度: %.1f °C\n", temp);
}

void app_main(void) {
    // 3. 创建默认系统全局事件总线
    esp_event_loop_create_default();

    // 4. 消费者向总线订阅 EVT_TEMP_UPDATE 事件
    esp_event_handler_instance_register(SYS_EVENT, EVT_TEMP_UPDATE, on_temp_update_ui, NULL, NULL);

    // 5. 生产者（传感器任务）采集到数据，向总线广播一条带载荷的事件
    float current_temp = 26.5f;
    esp_event_post(SYS_EVENT, EVT_TEMP_UPDATE, &current_temp, sizeof(float), portMAX_DELAY);
}
```

## 20.3 有限状态机（FSM）消除 `if-else` 地狱

在很多复杂设备（如智能门锁、扫地机器人、中控台）中，设备在不同阶段的行为截然不同：

```text
 ┌────────────────────────────────────────────────────────────────────────┐
 │                    【标准有限状态机 (FSM) 状态转移图】                 │
 │                                                                        │
 │                   ┌──────────────────────────┐                         │
 │                   │   BOOTING (开机自检中)    │                         │
 │                   └─────────────┬────────────┘                         │
 │                                 │ 自检通过 (EVT_SELF_TEST_OK)          │
 │                                 ▼                                      │
 │            ┌────────────────────────────────────────┐                  │
 │            │        STANDBY (低功耗待机中)          │                  │
 │            └───┬────────────────────────────────┬───┘                  │
 │   用户交互触发 │                                │ 传感器温度越限       │
 │ (EVT_ACTIVITY) │                                │ (EVT_OVERLIMIT)      │
 │                ▼                                ▼                      │
 │   ┌─────────────────────────┐      ┌─────────────────────────┐         │
 │   │   ACTIVE (活跃工作中)   │      │    ALARM (异常告警中)   │         │
 │   │   • 彩屏全亮            │      │    • 蜂鸣器长鸣         │         │
 │   │   • 开启网络上传        │      │    • 屏幕显示红色危险   │         │
 │   └────────────┬────────────┘      └────────────┬────────────┘         │
 │                │ 超时无操作                     │ 人工确认解除         │
 │                │ (EVT_TIMEOUT)                  │ (EVT_ALARM_CLEAR)    │
 │                └────────────────┬───────────────┘                      │
 │                                 ▼                                      │
 │                       返回 STANDBY 待机                                │
 └────────────────────────────────────────────────────────────────────────┘
```

* **状态机设计精髓**：
  * 用枚举定义清晰的 **状态（States）** 与 **事件（Events）**；
  * 用一个中心函数统筹状态转移逻辑，杜绝任何地方随手乱改全局变量！

#### 📄 有限状态机 (FSM) 核心代码骨架示范：
```c
// 1. 定义状态与事件枚举
typedef enum { STATE_STANDBY, STATE_ACTIVE, STATE_ALARM } sys_state_t;
typedef enum { EVT_USER_TOUCH, EVT_OVER_TEMP, EVT_TIMEOUT } sys_event_t;

static sys_state_t s_current_state = STATE_STANDBY;

// 2. 中心状态迁移处理函数
void fsm_handle_event(sys_event_t event) {
    switch (s_current_state) {
        case STATE_STANDBY:
            if (event == EVT_USER_TOUCH) {
                s_current_state = STATE_ACTIVE;
                printf("🔄 [状态迁移] STANDBY ──► ACTIVE (点亮屏幕)\n");
            }
            break;

        case STATE_ACTIVE:
            if (event == EVT_OVER_TEMP) {
                s_current_state = STATE_ALARM;
                printf("🚨 [状态迁移] ACTIVE ──► ALARM (蜂鸣器报警!)\n");
            } else if (event == EVT_TIMEOUT) {
                s_current_state = STATE_STANDBY;
                printf("🔄 [状态迁移] ACTIVE ──► STANDBY (熄屏待机)\n");
            }
            break;

        case STATE_ALARM:
            // 异常告警处理...
            break;
    }
}
```

## 20.4 高可用运维内功：看门狗 (TWDT) 与 Core Dump 诊断

### ① 硬件任务看门狗（Task Watchdog Timer / TWDT）
* **原理**：单片机内部有一个倒计时硬件定时器（比如设置 3 秒）。程序正常运行时，必须每隔一段时间向看门狗“喂一次狗（Feed Watchdog / Reset Counter）”；
* **自愈机制**：如果某个任务发生死锁（Deadlock）、死循环或硬件等待卡死超过 3 秒，看门狗超时立刻触发**芯片硬件级强行复位重启**，让死机设备自动恢复工作！

#### 📄 任务看门狗 (TWDT) 典型使用示范：
```c
#include "esp_task_wdt.h"

void sensor_task(void *pvParameters) {
    // 1. 将当前任务加入看门狗监控名单 (超时时间比如设为 3 秒)
    esp_task_wdt_add(NULL);

    while (1) {
        // 2. 正常工作：读取传感器
        read_sensors();

        // 3. 及时喂狗！重置 3 秒倒计时
        esp_task_wdt_reset();

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}
```

### ② Core Dump 崩溃内存转储与符号反解

#### ✈️ 生活化比喻：飞机的“黑匣子”
当飞机遭遇极端故障坠落前（对应程序发生空指针 `NULL` 访问或除以 0 导致 Panic 异常），黑匣子会在最后几毫秒内拼死记录下飞机的飞行高度、引擎转速与驾驶舱录音（对应 CPU 寄存器、RAM 局部变量与函数调用栈帧）。

#### 💾 Core Dump 保存在哪里？（2 种工业级存储目的地）

```text
 ┌────────────────────────────────────────────────────────────────────────┐
 │                    【ESP32 Core Dump 存储与分析全流程】                │
 │                                                                        │
 │   🔥 程序发生 Panic 崩溃 (如野指针 *ptr = 123)                          │
 │                          │                                             │
 │                          ▼                                             │
 │            【Panic Handler 异常接管引擎】                              │
 │                          │                                             │
 │          ┌───────────────┴───────────────┐                             │
 │          ▼ (方案 A：产线量产 / 掉电保存)   ▼ (方案 B：日常桌面调试)      │
 │  ┌─────────────────────────┐   ┌──────────────────────────┐            │
 │  │ 💽 写入 SPI Flash 专用分区 │   │ 🔌 经串口 UART 狂喷 Base64│            │
 │  │ (coredump 分区，掉电不丢)│   │ (idf.py monitor 实时捕获) │            │
 │  └───────────┬─────────────┘   └─────────────┬────────────┘            │
 │              │                               │                         │
 │              ▼ (售后/返修电脑读取)           ▼ (自动启动 GDB 反解)     │
 │  ┌────────────────────────────────────────────────────────┐            │
 │  │ 🎯 终端精准定位：main/app_main.c 第 48 行引发了非法内存访问!          │
 │  └────────────────────────────────────────────────────────┘            │
 └────────────────────────────────────────────────────────────────────────┘
```

1. **方案 A：保存在 Flash 专用分区（`Flash` 模式，最适合量产商用设备）**
   * **保存在哪**：保存在 ESP32 内部 SPI Flash 的一个独立分区（`coredump` 分区）中；
   * **最大优势**：**掉电不丢失！** 设备在野外死机重启后，崩溃瞬间的案发现场依然完好保存在 Flash 里。售后工程师用电脑连上板子，就能把“黑匣子”数据读取出来；
   * **分区表配置（`partitions.csv`）**：
     只需在分区表中加一行：
     ```csv
     # Name,   Type, SubType, Offset,  Size, Flags
     nvs,      data, nvs,     0x9000,  0x6000,
     phy_init, data, phy,     0xf000,  0x1000,
     factory,  app,  factory, 0x10000, 2M,
     coredump, data, coredump,0x210000,64K,
     ```

2. **方案 B：直接输出到串口 UART（`UART` 模式，最适合日常桌面开发）**
   * **保存在哪**：不占 Flash 空间，崩溃瞬间芯片通过串口以 Base64 编码文本形式打印到控制台；
   * **优势**：`idf.py monitor` 监视器会自动拦截这段 Base64 数据，配合本地编译生成的 `build/xxx.elf` 符号表，**秒级在终端上直接显示崩溃发生在哪一行 C 代码！**

---

#### 🛠️ 如何配置与提取 Core Dump？

1. **第 1 步：开启 Core Dump 功能**
   在终端运行：
   ```bash
   idf.py menuconfig
   ```
   进入：`Component config` ──► `Core dump` ──► `Data destination`，选择 **`Flash`** 或 **`UART`**。

2. **第 2 步：提取并反解 Flash 中的崩溃黑匣子数据**
   如果配置保存在 Flash 中，当设备发生异常重启后，在电脑终端运行官方提取工具：
   ```bash
   # 读取连接设备的 Flash coredump 分区，并配合 elf 文件精确定位代码行：
   espcoredump.py info_corefile -t raw -c COM3 build/esp32_journey.elf
   ```
   终端会输出类似于 GDB 的完整回溯（Backtrace）：
   ```text

   #1  0x40085678 in vPortTaskWrapper (pxCode=0x400d1230, pvParameters=0x0)
   ```
   **直接告诉你崩溃发生在 `main/app_main.c` 第 48 行！**

## 20.5 📚 核心库函数深度解析与参数字典（小白必读）

在 ESP-IDF 软件工程中，事件总线（`esp_event`）与看门狗（`esp_task_wdt`）是最核心的基石 API。下面逐一拆解每个核心函数的参数含义、内存机制与避坑要点。

---

### ① `ESP_EVENT_DEFINE_BASE` 与 `ESP_EVENT_DECLARE_BASE` —— 为事件建立“家族姓氏”

#### 1. ❓ 为什么需要它们？（解决什么痛点？）
在 ESP32 系统中，有成百上千种不同的事件：
* Wi-Fi 模块的事件枚举：`WIFI_EVENT_STA_START = 0`, `WIFI_EVENT_STA_CONNECTED = 1`...
* 蓝牙模块的事件枚举：`BLE_EVENT_SCAN = 0`, `BLE_EVENT_CONNECTED = 1`...
* 你自己写的业务系统枚举：`MY_TEMP_UPDATE = 0`, `MY_ALERT = 1`...

```text
 💥 严重冲突：
 如果只用一个数字传参，当收到 "ID = 0" 时，
 系统根本分不清这到底是【Wi-Fi 启动了】还是【温度更新了】！
```

* **解决方案（姓氏 + 名字）**：
  * **Base（姓氏 / 家族分类）**：`WIFI_EVENT`、`SYS_EVENT`；
  * **ID（名字 / 具体事件）**：`0`、`1`、`2`；
  * 组合起来 `(SYS_EVENT, 0)` 在整个系统中就是**绝对唯一**的！这两个宏就是用来给事件创建“家族姓氏”的。

---

#### 2. 🔍 这两个宏到底做了什么？（宏展开真相大揭秘）

```c
/* ==================== 1. 在 .h 头文件中声明 (让所有文件都能看见) ==================== */
// 你写的代码：
ESP_EVENT_DECLARE_BASE(SYS_EVENT);

// 编译器实际展开后的 C 代码：
extern const char *SYS_EVENT;  // 告诉所有文件：全局有一个叫 SYS_EVENT 的指针变量


/* ==================== 2. 在某一个 .c 文件中真正定义 (只写一次，分配内存) ==================== */
// 你写的代码：
ESP_EVENT_DEFINE_BASE(SYS_EVENT);

// 编译器实际展开后的 C 代码：
const char *SYS_EVENT = "SYS_EVENT"; // 在只读数据段真正为这个指针分配物理空间！
```

---

#### 3. ⚡ 底层高性能比对机制
* 当事件总线判断“收到的事件是不是 `SYS_EVENT`”时：
* 它**不需要做慢吞吞的字符串比较（`strcmp`）**！
* 而是**直接做指针物理地址比对（`base1 == base2`）**！在汇编级别仅需 1 条单周期指令即可完成匹配，性能强悍！

---

#### 4. 🏷️ 命名规则与多 Base 架构
* **名字是任意起的吗？**：可以，只要符合 C 语言变量命名规范（如 `SENSOR_EVENTS`, `UI_EVENTS`），不要与 IDF 内置的 `WIFI_EVENT` 等重名即可。
* **一个项目里面可以起多个吗？**：当然可以！大型项目强烈推荐按业务模块拆分多个 Base 频道（如传感器频道、UI 交互频道、网络通信频道）。

---

#### 💥 深度避坑：如果把这两个宏写反了，会发生什么？

* ❌ **把 `DEFINE` 写进 `.h`**：如果多个 `.c` 包含了该 `.h`，链接器会报 **`multiple definition of SYS_EVENT`（符号重复定义冲突）**！
* ❌ **只写 `DECLARE` 忘记写 `DEFINE`**：所有代码都找不到实体内存，链接器会报 **`undefined reference to SYS_EVENT`（未定义符号引用）**！

---

### ② `esp_event_loop_create_default()` —— 启动城市广播总站
* **函数原型**：`esp_err_t esp_event_loop_create_default(void);`
* 创建系统默认的事件分发循环后台任务，负责按序调度分发所有发布出来的事件。

---

### ③ `esp_event_handler_instance_register` —— 消费者订阅广播（重点剖析！）

* **函数原型**：
  ```c
  esp_err_t esp_event_handler_instance_register(
      esp_event_base_t       event_base,        // [参数 1] 事件基底 (哪个频道)
      int32_t                event_id,          // [参数 2] 具体事件 ID (填 ESP_EVENT_ANY_ID 监听全部)
      esp_event_handler_t    event_handler,     // [参数 3] 收到事件时的回调函数
      void                  *event_handler_arg, // [参数 4] 传递给回调的上下文指针 (可选，可为 NULL)
      esp_event_handler_instance_t *context     // [参数 5] 订阅实例句柄指针 (用于退订，可为 NULL)
  );
  ```

#### 🔍 5 大入参逐一拆解：
1. **`event_base`**：你关心的频段，如 `SYS_EVENT` 或 `WIFI_EVENT`；
2. **`event_id`**：你关心的具体事件（如 `SYS_EVENT_TEMP_UPDATED`）。如果填 `ESP_EVENT_ANY_ID`，代表“监听该频道下的所有事件”；
3. **`event_handler`**：回调函数指针，格式为 `void callback(void *arg, esp_event_base_t base, int32_t id, void *event_data)`；
4. **`event_handler_arg`**：传给回调函数的自定义参数（如 UI 屏幕上下文指针）；
5. **`context`**：退订句柄指针，若终身监听填 `NULL`。

---

### ④ `esp_event_post` —— 生产者向总线广播数据
* **函数原型**：
  ```c
  esp_err_t esp_event_post(
      esp_event_base_t  event_base,      // 事件基底
      int32_t           event_id,        // 事件 ID
      const void       *event_data,      // 数据载荷指针 (如 &sensor_data)
      size_t            event_data_size, // 数据字节大小 (sizeof)
      TickType_t        ticks_to_wait    // 阻塞等待超时时间 (如 portMAX_DELAY)
  );
  ```
* 💡 **深拷贝特性**：`esp_event_post` 会自动在堆上将载荷数据复制一份（Deep Copy），即使传入栈上的局部变量也是绝对内存安全的！

---

### ⑤ `esp_task_wdt_init` / `add` / `reset` —— 看门狗守护与喂狗
* `esp_task_wdt_init(&config)`：初始化任务看门狗守护超时（如 3000ms）；
* `esp_task_wdt_add(NULL)`：将当前任务加入看门狗监控护航名单；
* `esp_task_wdt_reset()`：**及时喂狗！** 刷新并重置看门狗倒计时。

### 2. 💻 实验 1 完整源码

> 📁 **配套源码文件**：[`code/20_software_architecture/01_bsp_decoupling/app_main.c`](../code/20_software_architecture/01_bsp_decoupling/app_main.c)  
> ⚡ **一键切换运行**：在终端运行 `./switch_code.ps1 20 1` 即可秒级切换并自动烧录！

```c
#include <stdio.h>
#include <stdbool.h>
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"
#include "driver/gpio.h"
#include "esp_log.h"

static const char *TAG = "EXP1_BSP_LAYER";

/* ==============================================================================
 * 🔧 一、 BSP 驱动抽象层 (底层：负责直接和硬件寄存器/引脚打交道)
 * ============================================================================== */
#define BSP_LED2_PIN      GPIO_NUM_27
#define BSP_BUTTON_PIN    GPIO_NUM_39

typedef enum {
    LED_STATE_OFF = 0,
    LED_STATE_ON  = 1,
    LED_STATE_TOGGLE
} bsp_led_cmd_t;

static bool s_current_led_state = false;

static void bsp_init(void)
{
    // 1. 初始化 LED2 输出引脚
    gpio_config_t led_cfg = {
        .pin_bit_mask = (1ULL << BSP_LED2_PIN),
        .mode = GPIO_MODE_OUTPUT,
        .pull_up_en = GPIO_PULLUP_DISABLE,
        .pull_down_en = GPIO_PULLDOWN_DISABLE,
        .intr_type = GPIO_INTR_DISABLE,
    };
    gpio_config(&led_cfg);
    gpio_set_level(BSP_LED2_PIN, 0);

    // 2. 初始化按键输入引脚
    gpio_config_t btn_cfg = {
        .pin_bit_mask = (1ULL << BSP_BUTTON_PIN),
        .mode = GPIO_MODE_INPUT,
        .pull_up_en = GPIO_PULLUP_DISABLE,
        .pull_down_en = GPIO_PULLDOWN_DISABLE,
        .intr_type = GPIO_INTR_DISABLE,
    };
    gpio_config(&btn_cfg);
    ESP_LOGI(TAG, "🔧 [BSP 硬件层] 底层 GPIO 与外设初始化完毕！");
}

static void bsp_led_control(bsp_led_cmd_t cmd)
{
    if (cmd == LED_STATE_TOGGLE) {
        s_current_led_state = !s_current_led_state;
    } else {
        s_current_led_state = (cmd == LED_STATE_ON);
    }
    gpio_set_level(BSP_LED2_PIN, s_current_led_state ? 1 : 0);
}

static bool bsp_button_is_pressed(void)
{
    return (gpio_get_level(BSP_BUTTON_PIN) == 0);
}

/* ==============================================================================
 * 💼 二、 业务应用层 (上层：纯业务逻辑，完全不知道具体是哪根引脚/芯片型号！)
 * ============================================================================== */
static void business_logic_task(void *pvParameters)
{
    ESP_LOGI(TAG, "💼 [业务逻辑层] 业务中枢任务启动运行...");

    while (1) {
        if (bsp_button_is_pressed()) {
            vTaskDelay(pdMS_TO_TICKS(20)); // 消抖
            if (bsp_button_is_pressed()) {
                ESP_LOGI(TAG, "🔘 [业务层感知] 用户触发了按键动作，切换灯光状态！");
                bsp_led_control(LED_STATE_TOGGLE);

                while (bsp_button_is_pressed()) {
                    vTaskDelay(pdMS_TO_TICKS(50));
                }
            }
        }
        vTaskDelay(pdMS_TO_TICKS(50));
    }
}

void app_main(void)
{
    ESP_LOGI(TAG, "==========================================================");
    ESP_LOGI(TAG, "   🚀 Level 20 实验 1：BSP 驱动层与业务逻辑解耦架构       ");
    ESP_LOGI(TAG, "==========================================================");

    bsp_init();
    xTaskCreate(business_logic_task, "biz_task", 3072, NULL, 5, NULL);
}
```

typedef enum {
    SYS_STATE_BOOT = 0,   // 开机自检中
    SYS_STATE_STANDBY,    // 低功耗待机
    SYS_STATE_ACTIVE,     // 活跃工作运行
    SYS_STATE_ALARM,      // 异常危险告警

    FSM_EVT_SELF_TEST_OK = 0,
    FSM_EVT_USER_ACTIVITY,
    FSM_EVT_TIMEOUT_IDLE,
    FSM_EVT_SENSOR_OVERLIMIT,

#### ② `services/sys_fsm.c`（状态机核心引擎）
```c
#include "sys_fsm.h"
#include "esp_log.h"

static const char *TAG = "SYS_FSM";
static sys_state_t s_current_state = SYS_STATE_BOOT;

const char* sys_fsm_state_to_str(sys_state_t state) {
    switch (state) {
        case SYS_STATE_BOOT:    return "BOOT (开机自检)";
        case SYS_STATE_STANDBY: return "STANDBY (低功耗待机)";
        case SYS_STATE_ACTIVE:  return "ACTIVE (活跃运行)";
        case SYS_STATE_ALARM:   return "ALARM (危险告警)";
        default:                return "UNKNOWN";
    }
}

esp_err_t sys_fsm_init(void) {
    s_current_state = SYS_STATE_BOOT;
    ESP_LOGI(TAG, "⚙️ [服务层] 有限状态机 (FSM) 模块就绪，初始状态: %s", sys_fsm_state_to_str(s_current_state));
    return ESP_OK;
}

void sys_fsm_handle_event(fsm_event_t event) {
    sys_state_t prev = s_current_state;
    switch (s_current_state) {
        case SYS_STATE_BOOT:
            if (event == FSM_EVT_SELF_TEST_OK) s_current_state = SYS_STATE_STANDBY;
            break;
        case SYS_STATE_STANDBY:
            if (event == FSM_EVT_USER_ACTIVITY) s_current_state = SYS_STATE_ACTIVE;
            else if (event == FSM_EVT_SENSOR_OVERLIMIT) s_current_state = SYS_STATE_ALARM;
            break;
        case SYS_STATE_ACTIVE:
            if (event == FSM_EVT_TIMEOUT_IDLE) s_current_state = SYS_STATE_STANDBY;
            else if (event == FSM_EVT_SENSOR_OVERLIMIT) s_current_state = SYS_STATE_ALARM;
            break;
        case SYS_STATE_ALARM:
            if (event == FSM_EVT_ALARM_CLEAR) s_current_state = SYS_STATE_STANDBY;
            break;
        default: break;
    }
    if (prev != s_current_state) {
        ESP_LOGI(TAG, "🔄 [FSM 状态跃迁] \033[33m%s\033[0m ➔➔➔ \033[1;32m%s\033[0m",
                 sys_fsm_state_to_str(prev), sys_fsm_state_to_str(s_current_state));
    }
}

#include "sys_guard_wdt.h"
#include "esp_task_wdt.h"
#include "esp_log.h"

static const char *TAG = "SYS_GUARD";

esp_err_t sys_guard_wdt_init(uint32_t timeout_ms) {
    esp_task_wdt_config_t twdt_config = {
        .timeout_ms = timeout_ms,
        .idle_core_mask = 0,
        .trigger_panic = true, // 超时触发 Panic 打印调用栈并转储 Core Dump 到 Flash
    };
    esp_err_t ret = esp_task_wdt_init(&twdt_config);
    if (ret == ESP_ERR_INVALID_STATE) ret = esp_task_wdt_reconfigure(&twdt_config);
    if (ret == ESP_OK) ESP_LOGI(TAG, "🛡️ [服务层] 看门狗守护就绪！(超时: %lu ms)", timeout_ms);
    return ret;
}

esp_err_t sys_guard_wdt_subscribe_current_task(void) {
    return esp_task_wdt_add(NULL);
}

esp_err_t sys_guard_wdt_feed(void) {
    return esp_task_wdt_reset();
}
```
